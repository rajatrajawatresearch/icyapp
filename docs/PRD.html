Mini marketplace app — Final requirements doc (v2)

Scale target: first ~2000 users Model: private-link customers (no signup/login), admin lists products, cash or manual-UPI-QR payment.

1. Roles & panels

User panel (customer) — no login

  • Opens a personal link (/u/<token>) — no signup, no password, no OTP
  • Browses products (name, price, image, stock)
  • Adds to cart, places order
  • Chooses fulfilment: Delivery (address) or Pickup
  • Chooses payment: Cash or UPI
  • If UPI: sees status go "waiting for QR" → "QR ready, pay now" → "payment confirmed"
  • Sees own order history (scoped to their token, nothing else)

Admin panel (seller) — real login

  • CRUD products (name, price, stock, image, category, active/inactive)
  • Customer list: add a customer (name, phone) → system generates their private link → admin copies/shares it (WhatsApp) → can revoke/regenerate anytime
  • Live incoming orders (poll-based badge/sound)
  • For UPI orders: upload QR image against that order, mark "sent"
  • Mark order paid (manual confirm), update status (confirmed → out for delivery/ready → completed → cancelled)
  • Payment records list (cash vs UPI, date, order ref)
  • Basic reports: today's orders, today's collection, pending UPI confirmations

Super admin panel — real login

  • Create/deactivate admin accounts
  • Platform-wide totals: orders, revenue, cash vs UPI split
  • Global settings: default pickup location, category master list
  • Audit log: who marked which order paid, who generated/revoked which customer link
  • Delete data (with safety window): delete button on any customer/order/product row. Clicking it doesn't delete instantly — it schedules deletion after a chosen delay (1 to X minutes, super admin picks from a dropdown, e.g. 1 / 5 / 10 / 30 min). During that window the row is hidden but an Undo button can cancel it. After the timer runs out, it's permanently removed from the DB. This avoids "oops, deleted the wrong thing" with no way back.

2. Customer identity — private link, not login

This replaces traditional signup entirely:

  • Every customer row has a unique token (random, unguessable — e.g. UUID or 12-char random string)
  • Their link is yourapp.com/u/<token> — visiting it resolves to that customer server-side, no session/password needed
  • Admin generates the link once when adding the customer, shares it manually
  • Admin can revoke a token (link stops working) and regenerate a new one anytime — this is a manual action, not automatic rotation
  • Token is checked server-side on every request to that customer's pages/orders — treat it like a bearer credential (long, random, HTTPS-only, not guessable), not a fully public URL

This is intentionally simple for ~2000 known customers. It is not meant for public self-signup — if that's ever needed later, real auth (OTP/password) would replace this layer without touching the rest of the schema.

3. Payment flow

  • Cash: order placed → admin marks paid on delivery/pickup → payment record created
  • UPI (as scoped for MVP): order placed (pending) → admin notified → admin uploads QR for that order → customer pays → admin manually marks paid → payment record created

Flagged earlier and still true: manual QR-per-order is fine to launch with, but doesn't scale past a few dozen orders/day without becoming a bottleneck. DB below is built so a future upgrade (one static UPI ID + auto-generated amount/reference, no manual QR upload) is a swap inside payments, not a redesign.

4. Database schema

customers — id, name, phone, token (unique, indexed), is_active, scheduled_delete_at (nullable), created_at

admins — id, name, phone/email, password_hash, role (admin/super_admin), created_at

products — id, admin_id, name, price, stock_qty, image_url, is_active, category, scheduled_delete_at (nullable)

orders — id, customer_id, status (placed/confirmed/paid/out_for_delivery/completed/cancelled), fulfilment_type (delivery/pickup), delivery_address (nullable), scheduled_delete_at (nullable), created_at

order_items — id, order_id, product_id, qty, price_at_order

payments — id, order_id, method (cash/upi), amount, status (pending/paid), qr_image_url (nullable), confirmed_by_admin_id, confirmed_at

notifications — id, admin_id, order_id, type (new_order/upi_pending), read_at

audit_log — id, actor_admin_id, action (e.g. "regenerated_token", "marked_paid"), target_id, timestamp

5. Tech stack — final

Picked for one solo dev, fast to ship, no over-engineering for 2000 users:

Layer Choice Why
Platform Mobile-first web app (not a native app) Customers open it via link in a mobile browser — no app store install needed. Built responsive so it feels like an app on phone, but it's just a website
Frontend + Backend Next.js (React + TypeScript) One codebase, API routes double as backend — no separate server to deploy/manage
Database PostgreSQL (via Neon or Supabase, hosted) Free/cheap tier comfortably handles 2000 users; room to grow
ORM Prisma Type-safe queries, easy migrations, pairs well with Next.js
Customer identity Token-based route (/u/<token>) — no session cookie needed for customers Matches the no-login model above
Admin/super-admin auth Simple email+password, hashed (bcrypt), session cookie or JWT Only ~a handful of internal accounts, doesn't need to be fancy
File storage (QR, product images) Supabase Storage or Cloudinary free tier Simple upload API, no need to run your own S3
Admin order notifications Polling every 5-8s on the admin dashboard Simplest reliable option at this scale — skip WebSockets/Socket.io until order volume actually needs it
Hosting Vercel (Next.js app) + Neon/Supabase (Postgres) Both have free tiers sufficient for MVP; zero server management

This whole stack avoids running your own backend server, a separate auth provider, or a message queue — all of which would be overkill at 2000 users and one dev.

6. API surface (rough)

  • GET /u/[token] — resolve customer, show product list + their orders
  • POST /api/orders — create order (customer_id from token, items, fulfilment_type, payment method)
  • GET /api/admin/orders — list orders (polled)
  • POST /api/admin/orders/:id/qr — upload QR image for an order
  • POST /api/admin/orders/:id/mark-paid — confirm payment
  • POST /api/admin/customers — add customer, generate token
  • POST /api/admin/customers/:id/regenerate-token — revoke old link, issue new
  • POST /api/admin/products — CRUD products
  • POST /api/superadmin/admins — create/deactivate admin accounts

7. MVP build order

  1. DB schema + Prisma setup
  2. Admin: add/edit products
  3. Admin: add customer → generate link
  4. Customer: open link → browse → place order (cash or UPI selection)
  5. Admin: see new order, upload QR (UPI), mark paid
  6. Order status updates, basic order history for customer
  7. Super admin: create admin accounts, view totals

Analytics, audit log detail, and multi-store support are v3+.

8. Still open (your call)

  • One store/admin only for now, or plan for more later?
  • Delivery — just collect address, or track a delivery person too?
  • UPI — stick with manual QR (Option A here) for MVP, or jump straight to auto-generated UPI link (no manual QR) if you'd rather skip that step from day one?
